# Deploying DevPilot — backend on Render, frontend on Vercel

DevPilot splits across two hosts: the FastAPI backend (needs a real container +
long-running requests + a writable filesystem) on **Render**, and the static
React UI on **Vercel**. Deploy the backend first so you have its URL for the
frontend.

> Honest limits of a live deploy: a PaaS has no Docker daemon, and running a repo's
> tests means executing untrusted code. Doing that inside the backend container would
> put it next to `DATABASE_URL`, `JWT_SECRET` and the Gemini key — so **the `local`
> backend is refused whenever `DATABASE_URL` is set** (hosted, multi-user mode;
> `ALLOW_UNSANDBOXED_LOCAL=true` overrides it, only if every user is trusted).
> Repair on the hosted demo instead runs through a **separate, secret-free test runner
> service** (section 1b). Without it, ingest and Q&A work and the "Fix a bug" mode
> reports why it is unavailable. The free Gemini tier also allows ~20 generate
> calls/day, so treat the live site as a demo, not a public service.

## 0. A Postgres database (for login, repos, and chat history)

Email/password login, ingested-repo metadata, chat history, and (with
`VECTOR_BACKEND=pgvector`) the embedded code chunks themselves all live in
Postgres. Render's free web service has **no persistent disk**, so without a
database, all of that lives on ephemeral disk / in the browser tab and
vanishes on every redeploy, restart, or reload. Use a free hosted Postgres —
**Supabase** is the quickest:

1. https://supabase.com → **New project** (free tier). Pick a region + DB password.
2. Project → **Connect** (or Settings → Database) → copy the **connection string
   (URI)**. It looks like
   `postgresql://postgres:<password>@db.<ref>.supabase.co:5432/postgres` (Supabase's
   string already requires SSL). The transaction **pooler** URI works too.
3. Keep this string — it's the `DATABASE_URL` env var in step 1.

The `users` table is created automatically on first boot. If you skip this step
and leave `DATABASE_URL` empty, the app still runs — just with **no login gate**
(open access), which is fine for a purely local/private demo.

## 1. Backend → Render

1. Push this repo to GitHub (done).
2. Render Dashboard → **New → Blueprint** → select this repo. Render reads
   [`render.yaml`](render.yaml) and creates the `devpilot-backend` Docker service.
   (Or **New → Web Service → Docker** and point it at [`Dockerfile`](Dockerfile).)
3. Set env vars in the service's **Environment** tab:
   - `GEMINI_API_KEY` = your `AIza…` key (the server's fallback key; visitors can
     also bring their own in the UI — see BYOK below)
   - `ALLOWED_ORIGINS` = your Vercel URL (fill in after step 2 below; you can
     start with `*` to test, then lock it down)
   - `DATABASE_URL` = the Postgres URI from step 0 (enables login)
   - `JWT_SECRET` = the blueprint generates one automatically; or set your own
     long random string. Signs login sessions — keep it secret.
   - `LLM_PROVIDER=gemini`, `GEMINI_MODEL=gemini-3.5-flash-lite`,
     `SANDBOX_BACKEND=local`, `VECTOR_BACKEND=memory` (already set by the blueprint)
4. Deploy. When it's live, note the URL, e.g. `https://devpilot-backend.onrender.com`.
   Health check: open `<url>/api/health` → `{"status":"ok","auth_enabled":true,...}`.

Free-tier note: the service sleeps after inactivity; the first request cold-starts
in ~30–60s.

## 1b. Test runner → Render (makes "Fix a bug" work on the hosted demo)

`render.yaml` also declares `devpilot-runner`, a small Docker service built from
[`runner/`](runner). It is the same idea as the Code Arena compiler service: the thing
that executes untrusted code is a **separate service that holds no secrets**.

- **What it does:** accepts a `.tar.gz` of a repo workspace and runs only
  `python -m pytest` on it. Auth is a bearer token (`RUNNER_TOKEN`, generated by Render
  and shared into the backend as `SANDBOX_TOKEN` automatically).
- **How it contains the code:** each run is dropped to its own unprivileged uid with a
  0700 directory; CPU, memory, process, file-size and open-file limits; a wall-clock
  timeout; a disk cap and an output cap; every process that uid owns is killed after the
  run; archives with links, devices or `..` are rejected. It **fails closed**: if it
  can't drop privileges it refuses to run anything (`/healthz` shows `isolation`).
- **What it can't do on the free tier:** block outbound network. It tells you so
  (`network_isolated: false`). It also doesn't install a repo's dependencies, so repair
  works on pytest-only Python repos such as the bundled samples.
- **One manual step:** after the runner is live, set **`SANDBOX_URL`** on the backend to
  its public `https://…onrender.com` address (see it on the runner's dashboard page),
  then redeploy. This is deliberately not auto-filled or guessed: the token and every
  uploaded workspace are sent to that address.
- **Check it:** `<backend>/api/health` → `"repair_enabled": true, "repair_runner": "remote"`,
  and `<runner>/healthz` → `"isolation": true, "ready": true`.

**Waking the runner (a real finding from testing on Render's free tier):** a sleeping
instance did *not* wake when the backend called it (every attempt got `502` for 100 s),
yet it woke within seconds when called from a browser or `curl`. So the **browser**
wakes it: the app pings `<runner>/healthz` once it's usable (`repair_wake_url` in
`/api/health`) and "Fix it" waits behind a visible *Wake the runner* step before it
submits the job. The backend still retries for up to `SANDBOX_WAKE_SECONDS` as a second
chance, and reports "tests not executed" rather than a fake result if the runner never
answers.

Repairs run as **background jobs** (`POST /api/agent/debug` returns a `job_id`;
`GET /api/agent/debug/{job_id}` reports live progress and the result), because a
repair can outlive a free host's request time limit, and the runner may need about a
minute to wake first. Each user can run one at a time and six per hour.

The bundled demo bugs (`examples/`) are indexed as `sample:<name>`. That is the only
way to index something from the server's own disk on a hosted deployment — arbitrary
local paths are refused unless `ALLOW_LOCAL_PATHS=true` (local development).

## 2. Frontend → Vercel

1. Vercel → **Add New → Project** → import this repo.
2. **Root Directory** = `frontend` (important — the app lives in that subfolder).
   Vercel auto-detects Vite ([`frontend/vercel.json`](frontend/vercel.json) sets
   build `npm run build`, output `dist`, and SPA rewrites).
3. Add an **Environment Variable**:
   - `VITE_API_BASE` = your Render backend URL from step 1
     (e.g. `https://devpilot-backend.onrender.com`)
4. Deploy → you get a URL like `https://devpilot.vercel.app`.

## 3. Connect them

1. Back in Render, set `ALLOWED_ORIGINS` to the exact Vercel URL
   (`https://devpilot.vercel.app`) and redeploy so the browser CORS check passes.
2. Open the Vercel URL, **create an account**, paste your own Gemini key if you
   have one, pick a repo, and try the agent.

## Bring your own key (BYOK)

The UI has an optional **"Your Gemini API key"** field. When a visitor pastes a
key there:

- it's stored **only in their browser** (localStorage) — never in our database
  or logs;
- it's sent with each request as the `X-Gemini-Key` header and used **only** for
  that request, then discarded;
- if no key is set, requests fall back to the server's `GEMINI_API_KEY`.

This is why the public demo doesn't die on the free-tier quota: each visitor
spends *their own* ~20 calls/day, not a single shared budget. Get a free key at
https://aistudio.google.com/app/apikey.

Both key formats work — the classic `AIza…` and the newer `AQ.…`. The backend uses
the `google-genai` SDK, which sends the key as an `x-goog-api-key` header; it never
inspects the key's prefix. Each key gets its own client object, so two visitors'
keys can never mix, even under concurrent requests.

## Password reset email (optional)

Without this, the app works fine; the login screen just says reset email isn't set
up. To turn on **Forgot password**, give the backend an HTTPS email provider (Render's
free tier blocks SMTP ports, so an API is required). Brevo is the easiest because
it only needs one verified sender address, not a domain:

1. https://brevo.com → sign up (free: 300 emails/day) → **Senders, Domains & Dedicated
   IPs → Senders → Add a sender** with an address you own, and click the verification
   link they email you.
2. **SMTP & API → API Keys → Generate a new API key.**
3. On Render, set these environment variables, then redeploy:
   - `BREVO_API_KEY` = the key from step 2
   - `MAIL_FROM` = the sender address you verified in step 1
   - `FRONTEND_URL` = your Vercel URL (already set by the blueprint)

(Resend works too: set `RESEND_API_KEY` instead of `BREVO_API_KEY`. Its free tier only
delivers to your own address until you verify a domain.) Check
`<backend>/api/health` — `"email_enabled": true` means it's on.

How it behaves: the emailed link works once, expires in 30 minutes, and carries its
token in the URL *fragment* (`/#reset=…`), which browsers never send to any server.
Asking for a reset always answers the same way whether or not the email has an account.
The link's address comes only from `FRONTEND_URL` / `ALLOWED_ORIGINS`, never from request
headers, and if neither names a real site the feature stays off.

## Account security

- **Lockout:** 5 wrong passwords for one email from one address, or 30 for one email
  overall or one address overall, within 15 minutes, answers `429` with `Retry-After`.
  Limits are held in memory, so they are exact on a single instance (Render's free
  tier) and per-instance if you scale out; multiple instances would need Redis.
- **Sessions:** every login token carries the account's session version. Changing or
  resetting a password signs out every other device, and deleting an account ends all
  of its sessions, within about 20 seconds across instances and immediately on the
  instance that handled the change.
- **Delete account** removes the user, every repo they ingested, all chat history, and
  the embedded chunks of any repo no other user shares.

## Tests and CI

`cd backend && python -m pytest tests -q` runs everything that needs no external
service. Set `TEST_DATABASE_URL` to a throwaway Postgres (with the pgvector
extension) to also run the real-SQL tests; **they drop the app's tables**, so never
point them at a real database. GitHub Actions
([`backend-tests.yml`](.github/workflows/backend-tests.yml)) does exactly that on
Python 3.11 with the pinned `requirements.txt`, and builds the frontend.
